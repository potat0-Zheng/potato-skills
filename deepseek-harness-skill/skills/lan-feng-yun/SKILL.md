# 揽风云 — 信息汇编技能

## 目标

围绕用户指定主题，通过多源搜索与交叉比对，汇总整理信息，产出结构化报告。**不做事实真伪判断**（那是 `/破虚妄` 的职责），专注于"把信息找到、理清、呈现好"。

## 运行模式

| 模式 | 用法 | 输出结构 | 适用场景 |
|------|------|----------|----------|
| `compile`（默认） | `/揽风云` | 信息汇编报告（8 章） | 信息汇总、材料整理 |
| `timeline` | `/揽风云 --mode timeline` | 事件时间线报告（7 章） | 事件脉络、时间线梳理 |

参数：`--summary`（精简输出）、`--scope`（限定范围，如 `--scope 官方`）、`--format markdown|json`（输出格式，默认 markdown，见「格式选项」）

## 工作流程

### 阶段 1：解析需求

从指令提取：主题、截止时间、范围约束、深度。若主题涉及国际/境外视角，先读 `references/foreign-media.md` 再进入阶段 2。

### 阶段 2：首轮搜索

并行 **2–4 次** WebSearch，搜索词设计原则：
- 至少一次中文 / 一次英文（国际语境）
- 覆盖不同角度：官方通报、媒体报道、数据/统计、立场/反应、**现场照片/视频截图**
- 搜索词之间有明确区分度，避免高度重叠

首轮即确定广度，后续只做缺口补充。若搜索结果含 `zhihu.com` 链接，走知乎 API 路径（见 `references/source-fallback.md`）。

### 阶段 3：缺口识别与补充

对照首轮结果，按维度查缺：

| 维度 | 检查项 |
|------|--------|
| 事实 | 时间、地点、参与方、结果是否完整 |
| 立场 | 各主要相关方表态是否覆盖 |
| 来源 | 官方/权威媒体/行业分析是否均有 |
| 地域 | 国内/国际视角是否平衡 |
| 时间 | 最新进展是否到截止时间 |
| 因果与语境 | 诱因/触发事件是否查明；主张是否只有被媒体截取的半句；有无断章取义警示信号 |

针对缺口执行 **1–2 次**补充搜索。停止条件：核心信息 ≥2 独立来源交叉确认、各方立场已获取、无明显空白。总量控制在两轮以内。

### 阶段 4：信息组织与标注

#### 4.1 主题聚类（碎片 → 主题）

将搜索结果中的碎片事实按四个维度打标签：
- **事件**：属于哪个具体事件/子事件
- **主体**：涉及哪些组织/人物/群体
- **争议点**：存在分歧或不同说法的问题
- **时间阶段**：是背景、进展、还是最新动态

然后聚类成 **2-4 个主题**，每个主题必须能用一句话说出中心（如"OPPO 文案事件：道歉 → 争议 → 官媒评论三阶段"）。聚类规则：
- 同主题碎片合并为一节，节内按时间或逻辑排列
- 无法归入任何主题的孤立碎片 → 并入「其他/补充」小节，并说明为何孤立
- 聚类不是标签堆砌——每个主题必须有一个**可检验的中心判断**（读者读完能复述"这节讲了什么"）

#### 4.2 去重合并（重复 → 合并）

同一事实主张被多个来源重复报道时，合并为一条，标注 `多源确认（N 家）[编号]`。规则：
- 一 URL 一编号，多源交叉确认标注多个编号（如 `[1][3]`）
- 合并后保留首次出现的编号顺序
- 合并时若各来源措辞/数字有出入，转入 4.5 冲突消解，不得静默取其一
- 同一稿件的门户镜像（标题/摘要高度近似、跨站转载）视为同一**转载簇**，只计 1 个独立来源；`多源确认（N 家）` 的 N 按独立稿簇计，不得把镜像当独立信源

#### 4.3 引用编号体系

每条事实性陈述末尾标注 `[编号]`，编号从 `[1]` 连续递增，指向来源索引。规则：
- 按首次出现顺序分配编号
- 图像引用以 `[图N]` 标注，与文字信源区分
- 推测/分析可引用编号，但不可包装为事实

#### 4.4 来源分级与确定性标记

**来源等级**（仅索引表中标注）：

| 等级 | 含义 | 示例 |
|------|------|------|
| A | 一手官方公报/正式文件 | 政府公告、法律文书 |
| B | 权威通讯社/官方媒体 | 新华社、央视、路透社 |
| C | 商业媒体/行业媒体 | 门户网站、行业刊物 |

**确定性标记**（正文内联，仅用于具体数字/数据）：

| 标记 | 含义 |
|------|------|
| ▲ | 官方渠道确认 |
| ● | 多家独立媒体一致，未经官方文件确认 |
| △ | 单一来源，或不同来源数字有出入 |

所有图像描述默认 △（模型无法视觉验证）；3+ 独立文字来源一致描述同一图像可升级为 ●。

涉及大量数字的汇编，可先用 `{SKILL_DIR}\scripts\extract_stats.py` 从抓取正文/摘要自动提取「数字+单位+上下文」结构化条目，供正文引用与复核（用法见脚本头注释）。

#### 4.5 冲突消解（冲突 → 消解）

数字或说法冲突时，**不只标 △ 罗列各说法**，必须继续分析冲突来源并给出判断：
- **口径差异**：统计口径不同（如"伤亡"是否含轻伤）→ 说明差异，不做强行统一
- **时间差异**：不同时点的数据更新（如"目前 X 人" vs "最新 Y 人"）→ 以最新为准并标注时间
- **立场差异**：不同立场来源的叙述冲突 → 并列呈现，标注各方信源等级
- 分析后给出「**更可信的一方 + 理由**」（依据：信源等级 / 一手 vs 二手 / 独立交叉确认数），措辞用"倾向于""证据支持"，不武断

### 阶段 5：撰写与检查

按输出规范组织报告。完成后做覆盖完整性检查：地域 × 主体 × 议题矩阵逐格核实，明确列出已覆盖/未覆盖项及原因。

同时核对三项汇总质量要求：
- **主题有中心**：每个主题都能一句话说清（4.1 聚类是否成立）
- **冲突已消解**：重复主张已合并（4.2），冲突说法已给出消解分析（4.5），而非仅标 △ 罗列
- **立场已均衡**：对立/少数观点显式覆盖并标注信源稀缺度（见输出规范第 3、6 章）

## 核心原则

- 搜索摘要（snippet）为默认信息获取方式，抓取仅在摘要不足时使用（策略链见 `references/source-fallback.md`）。
- Python 脚本单次任务 ≤3 次调用，环境未就绪则回退。
- 禁止用外媒中文版替代英文原站；禁止对同一 URL/被阻断域名反复重试。
- **汇总优先于罗列**：重复信息必须合并、冲突必须消解、碎片必须聚成主题。报告的价值在降低读者的认知负担，不在穷尽信源。
- **结论先行**：compile 报告开头必须有「一句话结论 + 3-5 条关键要点」，细节作为证据层跟在后面。
- **立场均衡**：对立/少数观点必须显式覆盖并独立标注，禁止让报告被主流叙事单边化。

## 执行环境契约（DSH/Windows）

- 含中文的 Python 脚本不可 `python -c` 内联；先 Write 到 `.py` 文件再执行。
- Python 中文输出一律写 UTF-8 文件后 `read`（避免 stdout GBK 报错）；执行前设 `$env:PYTHONIOENCODING='utf-8'; $env:PYTHONUTF8='1'`。
- 向脚本传 JSON 参数先落盘为 `.json` 文件再传路径（避免 PowerShell 引号吞掉 JSON）。

## 输出规范

### 模式一：信息汇编报告（`compile`）

1. **结论速览** — 一句话核心结论 + 3-5 条关键要点（30 秒读完层，细节见后）
2. **任务概述** — 一句话概括需求和范围
3. **核心内容** — 按主题组织（2-4 个聚类主题，每个主题一句话中心 + 支撑条目）。事实陈述标 `[编号]`，图像标 `[图N]`。原文引用块保留来源名称。确定性标记（▲/●/△）内联于数字之后。**对立/少数观点独立小节**，标注「该立场信源稀缺」或列出其信源及等级
4. **来源索引** — `[编号]` 来源名称、URL、等级（A/B/C）、类型。按首次出现顺序排列
5. **图像附录** — 可选。每项含 `[图N]`、声称内容（snippet/配文描述）、出处、URL、视觉验证状态（默认"未验证 △"）
6. **覆盖完整性声明** — 已覆盖/未覆盖维度，未覆盖项注明原因；含**立场维度**（哪些立场已覆盖、哪些稀缺或缺失）
7. **方法论说明** — 搜索轮次、搜索词设计、来源数、引用主张数、**聚类/去重统计**（原始信源 N 条 → 聚类 M 个主题 / 合并后 P 条）
8. **汇编时间戳** — 信息截止时间、汇编完成时间、事件跨度

### 模式二：事件时间线（`timeline`）

1. 事件概述 → 2. 时间线（日期+描述+`[编号]`）→ 3. 各方反应（按主体分类）→ 4. 关键节点分析 → 5. 来源索引 → 6. 图像附录（可选）→ 7. 汇编时间戳

### 摘要模式（`--summary`）

精简核心内容 + 来源列表。不输出完整章节。

### 格式选项（`--format`）

| 格式 | 输出 | 适用 |
|------|------|------|
| `markdown`（默认） | 报告正文为 Markdown（各模式的默认形态） | 人读、贴入 Obsidian |
| `json` | 结构化 JSON（compile 模式 schema 见下） | 喂给下游 skill 或程序化消费 |

**compile 模式的 `json` schema**：

```json
{
  "title": "报告标题",
  "format": "compile",
  "summary": "一句话核心结论",
  "key_points": ["要点1", "要点2"],
  "topics": [
    {"title": "主题名", "center": "一句话中心",
     "items": [{"text": "事实陈述", "refs": [1, 3], "certainty": "▲"}]}
  ],
  "standpoints": [
    {"side": "立场名", "coverage": "覆盖|稀缺|缺失", "refs": [4, 6]}
  ],
  "sources": [
    {"id": 1, "name": "来源名", "url": "https://...", "grade": "A|B|C", "type": "类型"}
  ],
  "meta": {"search_rounds": 2, "source_count": 8, "merged_count": 6,
           "topic_count": 3, "as_of": "信息截止时间", "compiled_at": "汇编完成时间"}
}
```

json 输出同样必须满足全部汇总质量要求（聚类、去重、冲突消解、立场均衡、结论速览）——schema 只是传输形态，不是质量豁免。

## 注意事项

- **不做真伪判断**：不区分事实与谣言。需核查 → `/破虚妄`
- **信息截止点**：必须标注，注明搜索引擎索引延迟可能遗漏最新信息
- **可追溯信源**：每条事实标 `[编号]`，URL 集中索引。设计目标：正文 +4 字符/条，避免 URL 内联造成 ~30% token 膨胀
- **不确定性坦诚**：数字出入不做强行统一，标 △ 列各说法；但 △ 之后必须给出冲突来源分析（口径/时间/立场）与更可信一方的判断（见 4.5），不得止步于罗列
- **立场均衡**：对立/少数观点显式覆盖并标注信源稀缺程度，防止报告被主流叙事单边化
- **汇总质量自检**：交付前核对——重复已合并、冲突已消解、主题有中心、结论有速览；做不到的在「覆盖完整性声明」中显式说明
- **搜索节制**：两轮以内。本技能价值在**整理**，穷尽不如清晰
- **与 `/破虚妄` 关系**：`/破虚妄` ="这事是真的吗"，`/揽风云` ="关于这事都有哪些说法"
- **与 `/百宝袋`、`/破虚妄` 关系（三技能联合汇编）**：遵行 `~/.dsh/report-theme/CONTRACT-joint.md`；本技能在采集完成后承担信息聚类、冲突消解与来源索引部分。细则以契约文件为准，本处不重复。
- **事件进行中**：不下确定性结局/走势判断，只作情景表述（如"若官方不回应则 X；若继续发文则 Y"），并注明为动态快照（见 CONTRACT-joint §5）。
